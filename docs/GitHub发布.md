# GitHub 正式发布与自动更新

自动更新仓库为 `MAxiangm/shitu-releases`。本地生成安装包、提交源码、推送分支或保存 Release 草稿，都不代表新版本已经向用户发布。客户端读取 GitHub 的最新正式 Release；草稿和预发布版本不会进入正式更新通道。

## 本地正式发布

1. 更新 `package.json` 的稳定版本号，完成检查、测试和安装包构建。
2. 只提交源码、文档及构建配置，然后将源码提交推送到远端。不要提交 `.recovery`、`dist`、用户素材库或本机日志。
3. 确认当前提交与安装包源码一致，取得完整提交 SHA：`git rev-parse HEAD`。
4. 发布完整资源：`node scripts/publish-github.cjs --publish --target <完整提交SHA> --notes-file release-notes.md`。

省略 `--target` 时，发布器使用本地 `HEAD` 的完整 SHA。它会确认该提交已经存在于远端，已有同名标签也必须指向此提交。创建 Release 时显式指定目标提交，避免给旧源码打上新版本标签。

发布器先创建草稿，上传 ASCII 名称安装包 `shitu-<版本>-setup.exe` 与 `shitu-update.json`，逐一核对上传状态、大小和 SHA-256，全部正确后才公开并标记为 Latest。公开后还会以匿名、禁用缓存的请求检查 `/releases/latest` 和固定版本的更新清单；只有验证成功才输出 `Published`。

不加 `--publish` 只生成草稿，客户端看不到此版本。已经正式发布的安装包不会覆盖；修复内容应使用新版本号。

## 发布后的公开验证

如果公开完成后因网络、缓存或 GitHub 服务响应导致验证未通过，脚本会明确提示“已发布，但匿名公开验证失败”。此时不要重新创建同名 Release 或替换附件，先检查 GitHub 页面与网络，再运行：

`node scripts/publish-github.cjs --verify-only`

此命令只检查当前项目版本和本地 `dist` 对应资源，不创建、修改或重新发布版本。安装包和清单的大小、摘要，以及用户实际能够取得的清单，必须一致。

## GitHub Actions

推送 `v<版本>` 标签可以让 Actions 测试、构建并发布。标签必须与该提交的 `package.json` 版本一致。

如果该标签已由本地发布器完整正式发布，轻量预检查会验证现有公开附件和清单，然后跳过重复构建、发布。手动运行 `workflow_dispatch` 始终执行测试构建，只上传校验产物，不自动发布正式版本。不要同时对同一个尚未发布的标签启动两条发布流程。

## 用户何时看到更新

0.13.1 起，启动后尽快检查更新，运行期间每 5 分钟检查；回到应用或网络恢复时也会在节流后检查。手动“检查更新”立即发起新请求，不复用旧缓存。旧版客户端需先点击检查或重启升级，已经安装的旧检测间隔无法远程修改。

正式发布并通过公开验证后，新版本即可被后续检查请求发现。GitHub、网络连接和客户端检查时机仍有延迟，不能承诺所有用户在发布瞬间收到通知。GitHub 匿名 API 每个公网 IP 每小时限 60 次，请勿使用每秒轮询，也不要将发布凭证放进客户端；严格实时通知需要额外的推送服务。
